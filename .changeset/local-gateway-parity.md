The local gateway answers the way API Gateway and the gateway runtime do. A request goes to the most specific route: a literal segment wins over a path parameter and both over a greedy one, a method route wins over an `ANY` route, and a greedy parameter such as `{proxy+}` takes the rest of the path (as `proxy`). With `cors` declared, CORS follows the configuration the deploy gives API Gateway: headers only for an allowed origin, a preflight no route takes answered with 204, and the handler's own `access-control-*` headers replaced; without `cors`, responses carry no CORS headers and a preflight goes to the routes as any request. The Lambda of a route and of its authorizer gets `max(5, timeout - 1)` seconds (the route `timeout`, then the service default, then 30), the `Timeout` event comes a second before the deadline, and past it the gateway answers 500 `{"message":"Internal Server Error"}` while the handler keeps running and its result is dropped. An error that is neither an `HttpError` nor in `httpErrors` answers 500 without its message, a mapped `ServiceError` carries `context`, and responses the handler produces carry `x-trace-id`. Each HTTP and WebSocket invocation runs in a scope of its own, so concurrent requests no longer overwrite each other's trace id. WebSocket connections close after 10 minutes idle or 2 hours open (`idleTimeout` and `connectionDuration`, in seconds, under the service's `localOptions` or `testOptions`), and `sendMessage` to a connection that is gone resolves, as the AWS client does with `GoneException`. The local HTTP client sends through the `fetch` of the moment it loads, so a spec that stubs `globalThis.fetch` no longer intercepts emulator traffic; mock the client with `HttpTester.setClientMock` instead. `getCorsConfiguration` moved to `@ez4/gateway/library`. Serve errors carry CORS headers too. Run the consumer's suite before upgrading: a test that expected the message of an unmapped error, or intercepted an ez4 HTTP client through `globalThis.fetch`, now fails.
